### Decisions (with reasons)
- **How the counterfactual programs are made (step 1):** `data/generate_counterfactual.py` transforms existing seed programs mechanically, so no new English is written by me (or any hosted AI): it drops one filter condition on a column C that the program reads nowhere else, removes C from the policy's `allow read` list for that sheet (write permission is kept), and leaves C in the sheet declaration as the tempting column. Each result passes parse + checker + 3 monitored runs; a test also checks that putting the dropped condition back makes the checker reject it with E401, so the counterfactual really forbids the column the program would naturally use. Nothing equals a dev or held-out program, sheet declaration or `about` line (checked by reading those task files only). Result: 1017 verified candidates, **534 selected**, round-robin over columns with `status` capped at 300: **20 distinct columns** (status 300, ready_on 30, renews_on 26, expires_on 22, ordered_on 21, held_until 20, due_date 18, sent_on 16, ...), 199 of them trap programs, 201 derived from seed programs whose original (column allowed) version is already in the training data (a deliberate contrast pair).

Trap tasks (30): v0.2 fails mostly by not parsing (8); q7b-v2 fails mostly with E401 (12 of 30 trap tasks at both epochs). Business types: every type has only 5 tasks, so per-type counts are too small to mean much; the types where q7b-v2 epoch 2 failed all 5 are event venue and thrift store (v0.2: escape room, kids' summer camp, physiotherapy clinic).

**E401 gap: known.** It is the same 110 tasks for both models, and on the 25 tasks where epoch 2 hits E401, v0.2 hits E401 on only 1 (v0.2 is correct on 7 of them, e.g. coffee-05, hw-01, tattoo-05, cater-04, optom-02). So the tasks do not force the error. In all 25 cases (and all 22 at epoch 1) the program names the policy it was given, but then reads (21) or writes (4) a column that policy does not allow. So the model keeps the policy line and ignores the policy's allow-list. In 24 of 25 cases the column exists in the task's sheet but the owner's request does not mention it by name (examples: coffee-04, coffee-05, hw-01, tattoo-02, tattoo-03); in 1 the request mentions it (move-03). The word match cannot see synonyms, so "not mentioned" is approximate.
**E401 cause: partly a guess.** The most common forbidden column is `status` (8 of 25); `status` appears in a filter/where/set line of 2,254 of the 2,401 training programs, so a trained habit of filtering on `status` is a likely reason for those 8. But 12 of the 25 columns (`plan`, `last_exam`, `reorder_at`, ...) appear in no training program at all (counts in the same file), so the habit explanation does not cover them; the model seems to pick the column that sounds right for the request even when the policy only allows a different one. That second part is a guess, not tested.

**2. Memorisation: weaker evidence than the session-2 note suggested.** Epoch 2 reuses a training `about` line in 26 outputs (epoch 1: 28, v0.2: 6). Those outputs are **not** more often wrong: 10 of 26 correct (38%) vs 22 of 84 (26%) for outputs without a reused line (epoch 1: 12/28 vs 20/82; v0.2: 2/6 vs 32/104). By statement skeleton (names, strings and numbers removed), 19 of the 26 are at least 90% similar to the training program with that `about` line, but they are almost as similar to the task's own reference program (median 0.939 vs 0.904), because most Aether programs share one shape. So: known that the model reuses `about` wording; not shown that it copies whole programs or that reuse causes failures. Examples of a copied skeleton that is wrong: physio-02, hw-01, hw-02, tattoo-02, tattoo-05.

## GPU admission correction (2026-10-25)

Owner decision: GPU admission passes when GPU memory meets the existing threshold and no other Aether GPU job holds a live PID in `logs/gpu.lock`. Desktop apps and unreadable process names must produce warnings, never a process-based failure. This supersedes the earlier conservative Windows process rule; historical setup results above are unchanged.

Implemented in `stages/gpu.py`, shared by preflight, the load probe, and stage scripts. GPU memory remains a separate required check. The PID lock is acquired before work and removed on normal completion, Python exceptions, SystemExit, or keyboard interruption. A hard-killed job can leave a PID file, which is ignored/replaced when its PID is dead. Windows PID checks use a read-only process handle, never `os.kill` or process termination. No process names are used to decide whether an Aether job exists.

A small OS-locked sidecar (`logs/gpu.lock.guard`) serializes PID-file creation, stale replacement, and removal. This prevents simultaneous starters from both replacing a stale PID file and entering. The sidecar remains on disk, but its OS lock is automatically released on a crash. Both files are already ignored by the existing `logs/` gitignore rule. A malformed PID file stops with an explicit inspection message rather than guessing who owns it.

Stage 3, stage 4, and load-smoke entry points hold the lock around their work. Stage 5 starts each evaluator through `python -u -m stages.gpu eval.baseline` (or repair/constrained); the runner executes the evaluator in the same process whose PID is recorded. A parent orchestrator crash therefore cannot make a still-running evaluator look dead. Preflight does not reserve the GPU for a later job; each actual job performs its own atomic admission check. Scripts launched outside these guarded entry points do not participate in the PID protocol.
